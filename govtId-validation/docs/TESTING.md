# Test Strategy

## Principle

Each test targets a **property the design depends on**, not a line of code. Coverage is a
by-product; the question every test answers is "which design guarantee breaks silently if
this regresses?"

This matters more than usual here. Most defects in a screening platform are *silent*: a
detector that stops firing, a threshold that drifts, a normalisation that starts rejecting
valid names. None of them throw. They just quietly change what the system concludes about
people.

## Current suite — 88 backend tests, 58 face service tests

```bash
cd backend && ./mvnw test                      # 88
cd face-verification-service && pytest -q      # 58
```

### Face service — `face-verification-service/tests`

| Suite | Guards |
|---|---|
| `TestNoFalsePositives` | No combination of bad evidence yields a MATCH — swept across the whole score range |
| `TestNoFalseAccusations` | A poor image is never turned into an impostor accusation either |
| `TestDecisionBands` | Threshold bands, including the margin that makes a borderline score uncertain |
| `TestQualityAssessor` | The quality gate, on synthetic images with known defects |
| `TestYuNetRowLayout` | The detector's output indices — see below |
| `TestUncertaintyIsExplained` | An uncertain result always carries reasons and advice |
| `TestLivenessDetector` | Texture, size-ratio and aggregation heuristics |

The central property is **one-sided**: the system may be wrong by being unsure, but it
must not be wrong by being confident. Every path that could produce a MATCH on evidence
that does not support one is asserted.

> `TestYuNetRowLayout` exists because of a real bug. YuNet returns
> `[x, y, w, h, 10 landmark coordinates, score]` — the score is the **last** element. The
> code read index 4, which is the right eye's x-coordinate, and took landmarks from indices
> 5–14, shifting every one by half a coordinate. Those shifted landmarks fed the alignment
> step a face warped to the wrong canonical position, degrading every embedding and pulling
> unrelated faces together.
>
> It threw nothing. It surfaced only as slightly worse scores. That is exactly the class of
> defect this suite exists to catch, so the layout is now pinned.

Integration tests run against an **embedded MongoDB**, so the suite needs no Docker daemon
and no local `mongod`.

> Stop any running `spring-boot:run` before testing. On Windows a live instance holding
> `target/classes` crashes the surefire fork with "The forked VM terminated without properly
> saying goodbye" — a build failure that looks like a test failure and is not.

## What each layer proves

### Standards conformance — `MrzParserTest`

Tested against the **published ICAO 9303 specimens** (the Utopia passport and TD1 card),
not against fixtures generated by the parser itself. A self-generated fixture would agree
with a broken implementation and prove nothing.

Coverage: full field extraction for TD3 and TD1; all check digits valid on a genuine MRZ;
each tamper mode detected separately — altered date of birth, altered document number, and
an edit that keeps every field digit but breaks only the composite; MRZ located inside a
full page of OCR text; absence reported rather than guessed; impossible calendar dates
rejected without throwing.

The check-digit arithmetic is additionally asserted against known values, which is what
lets the integration test build its own valid MRZs safely.

### Rule correctness — `DocumentValidationServiceTest`

A fixed `Clock` (2026-08-27) makes every expiry and validity rule assertable. The suite
starts from one valid passport and perturbs a single field per test, so a failure names the
rule that broke.

Two tests exist purely to guard against over-eager matching:

- **`toleratesTransliteratedName`** — `MÜLLER` on the page against `MUELLER` in the MRZ must
  *not* raise a mismatch. Without this, every traveller with a non-English name generates a
  forgery finding.
- **`acceptsIcaoSpecialCodes`** — `XXB` (refugee) and `D` (Germany) are valid, though
  neither is an ISO country code. Without this, stateless and refugee travellers are flagged.

### Mathematical properties — `RiskEngineTest`

The scoring model's guarantees are asserted directly because they *are* the contract:

- **Saturation** — twelve `LOW` findings must score below one `CRITICAL`.
- **Boundedness** — forty criticals stay within 0–100.
- **Monotonicity** — adding evidence never lowers the score.
- **Order independence** — reversing the module list does not move the verdict.
- **The coverage rule** — a `FAILED` module blocks `CLEAR`; a `SKIPPED` one does not.

### Detector behaviour — `CopyMoveDetectorTest`

The two cases that decide whether the detector is usable at all, on a fixture built to look
like a real document — gradient paper, dense guilloche, distinct printed fields, and a
uniform capture-noise floor, round-tripped through JPEG:

1. **Silent on security printing.** Guilloche and microprinting genuinely produce many
   matches at a consistent offset. Reporting them makes the detector worthless.
2. **Catches a real paste, and localises it.** The test asserts the reported shift vector and
   region bounds, not merely that *something* fired. A detector that flags the wrong place
   is not much better than one that stays silent.

This pair is the regression guard for every threshold in that detector. Anyone loosening a
constant in `CopyMoveDetector` must keep both passing.

The fixture deliberately uses **distinct** printed field labels. An earlier version repeated
one line eight times, which is real duplication — the test was measuring content the fixture
had created.

### Aggregation logic — `TamperingServiceTest`

Stub detectors isolate the service from real image analysis:

- One detector raising three findings must **not** claim corroboration. This is a regression
  test for a shipped bug where findings were counted instead of techniques, letting one
  detector's three observations read as three independent confirmations.
- Three detectors each raising one finding **must** corroborate.
- A `LOW` observation does not count towards corroboration.
- A detector that throws does not stop the others.
- An undecodable upload is reported as a finding, not a module failure.

### End to end — `ScreeningPipelineIntegrationTest`

The full pipeline against a real database, using a synthetic JPEG and MRZs built with
independently verified check-digit arithmetic:

- A sound passport clears, with all five stages reporting.
- An altered date of birth is caught and the case does not clear.
- An expired document is flagged.
- A watchlisted document is rejected with score ≥ 70.
- One document under two identities is detected.
- One identity with two documents is detected.
- An officer decision is recorded *alongside* the recommendation, not over it.
- **With no OCR engine available, a case is still produced and is not cleared** — the
  coverage rule verified through the whole stack.

## Manual verification performed

Automated tests use synthetic imagery. The detector tuning was validated against
document-like images through the running API:

| Input | Result |
|---|---|
| Realistic passport page | 6 / LOW / CLEAR — one informational metadata note |
| Same page, MRZ date of birth altered and a region duplicated | 75 / CRITICAL / REJECT — check digit, composite, copy-move, cross-identity |

Before detector tuning the clean page scored 61 / HIGH / REVIEW with five false positives.
That before/after is the evidence the thresholds are doing real work.

## Gaps

Stated plainly, because a test suite that is trusted beyond its scope is a liability.

- **No labelled corpus.** Thresholds are reasoned from first principles and validated on
  synthetic and synthetic-realistic documents. **No precision or recall figure should be
  quoted for any detector** until it has been measured against genuine and known-forged
  documents. This is the single most important outstanding quality task.
- **No frontend tests.** The console is untested; the module-status defect was found by
  inspection, not by a test.
- **No load testing** at checkpoint volumes.
- **No adversarial testing.** Nobody has tried to build a forgery specifically to evade these
  detectors, which is the test that matters most for a security control.
- **Module 4 untested end to end** — no biometric service exists to test against.
